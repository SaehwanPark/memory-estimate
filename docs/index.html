🎯 Purpose & Core Overview

Running local LLMs for agentic coding (e.g. Cursor, Claude Code, Aider, Roo Code) is fundamentally different from running simple one-shot conversational chatbots. Coding agents maintain extensive context windows (32k to 128k+ tokens) loaded with repository file trees, AST outlines, compiler diagnostics, and iterative tool outputs.

At 64k or 128k context depth, KV Cache memory frequently exceeds the size of the model weights themselves. This tool fetches real Hugging Face metadata, inspects remote GGUF binary headers via range requests, groups sharded files, and computes realistic Unified RAM requirements.

📚 Background & Technical Concepts

1. Unified Memory vs. Discrete GPU VRAM

On Apple Silicon (M1/M2/M3/M4), CPU and GPU share a single physical memory pool called Unified Memory. Unlike discrete NVIDIA graphics cards that have dedicated VRAM, macOS must share memory between the LLM weights, the KV cache, the macOS kernel, the WindowServer, multi-monitor display framebuffers, and developer tools (VSCode/Cursor, browser, Docker).

The Swapping Penalty: If LLM allocation exceeds physical memory, macOS immediately begins compressed memory swapping to NVMe SSD. In LLM inference, this destroys generation speed from 25-40 tokens/sec down to 0.5 tokens/sec.

2. What is the KV Cache in Agentic Coding?

During transformer inference, previously evaluated Key and Value vector representations of tokens are retained in memory so they do not need to be recomputed for each generated token.

In agentic coding, each turn can add thousands of tokens. At 64,000 tokens on a 32B model:

  • Standard FP16 KV Cache: ~17.2 GB
  • 8-bit (q8_0 / FP8) KV Cache: ~8.6 - 9.1 GB (recommended memory-efficient default; quality impact is generally small but model/backend dependent)
  • Q4_0 KV Cache: ~4.8 GB (block scale metadata included; 4.5 bpw)

3. Attention Architectures Compared

  • MHA (Multi-Head Attention): Equal number of query, key, and value heads. Massive KV cache footprint.
  • GQA (Grouped-Query Attention): Multiple query heads share a single key/value head (e.g. 8:1 ratio in Llama 3.1 70B or Qwen 2.5 32B), reducing KV cache size by 4x to 8x.
  • MLA (Multi-Head Latent Attention): Used in DeepSeek V2/V3 and GLM-5. Key and Value projections are compressed into a low-rank latent vector (kv_lora_rank = 512). Achieves ~5x KV cache compression over standard GQA!
  • Hybrid Linear Attention: Used in models like GLM-5.3-Flash and Qwen3.6 MoE. Only a fraction of layers use full/sparse attention, while the majority use linear recurrent attention with fixed state memory.

4. Epistemic Decomposition & Precise Block Sizing

Memory estimation is decomposed into four explicit confidence tiers:

  • Model Weights (Mweights): Exact downloadable shard bytes summed via Hugging Face API (or parameter heuristic if unquantized base model).
  • KV Cache (MKV): Architecture-derived calculation accounting for full-attention layers (Nfull), linear attention recurrent state (Nlinear × Sstate), and real GGML block quantization scales (q8_0: 8.5 bpw / 1.0625 B, q4_0: 4.5 bpw / 0.5625 B, q5_0: 5.5 bpw / 0.6875 B). Supports asymmetric K and V quantization.
  • Activation Scratchpad (Mscratch): Backend heuristic modeling attention workspace, context graph, MoE routing buffers, and prefill chunking (ubatch).
  • System Headroom (Mheadroom): User policy reserve (default 6.0 GB) for macOS kernel, WindowServer, framebuffers, and IDE tools.

5. macOS Metal Working-Set Limit vs. Physical RAM

Apple Silicon memory planning evaluates two distinct constraints:

  • Physical RAM Fit: Total memory must fit within system RAM (Mtotal ≤ MRAM) to avoid catastrophic SSD swap.
  • Metal Working-Set Limit (~75%): macOS limits a single process's GPU/Metal allocation to ~75% of physical RAM by default (Mruntime ≤ 0.75 × MRAM). When runtime memory fits in RAM but exceeds 75%, macOS may fail allocation unless tuned via sudo sysctl iogpu.wired_mem_limit.

Step-by-Step Workflow

  1. Select or Paste Model URL: Enter any Hugging Face URL (e.g., https://huggingface.co/unsloth/GLM-5.3-Flash-GGUF or https://huggingface.co/unsloth/Qwen3.6-35B-A3B-UD-MLX-3bit), or select a preset.
  2. Select Quantization Variant: The app automatically lists all detected quantizations with their exact shard counts and byte sizes (e.g. UD-Q3_K_XL, UD-QD3_XXS, UD-MLX-3bit [Repo Exact]).
  3. Configure Agentic Parameters: Adjust context window depth slider (32k to 128k+ tokens), K and V cache quantization types (e.g. fp16, fp8, q8_0, q4_0, q5_0 with asymmetric options), and system headroom reserve (default: 6.0 GB).
  4. Review Memory Allocation & Hardware Sizing: Inspect the live stacked breakdown and the Apple Silicon Hardware Compatibility Matrix with status badges.

📚 배경 지식 및 핵심 용어 설명

1. 통합 메모리(Unified Memory)와 외장 VRAM의 차이점

Apple Silicon(M1/M2/M3/M4)은 CPU와 GPU가 통합 메모리라는 단일 물리 풀을 공유합니다. 독립된 VRAM을 가진 NVIDIA 외장 그래픽 카드와 달리, Mac에서는 LLM 가중치와 KV 캐시뿐만 아니라 macOS 커널, WindowServer(디스플레이 합성기), 4K/5K 외장 모니터 프레임버퍼, 그리고 개발자가 실행 중인 IDE(Cursor, VSCode), 브라우저 등이 메모리를 함께 사용합니다.

스와핑(Swapping) 병목 현상: 실행 중인 LLM 메모리가 물리 통합 메모리를 초과하면, macOS는 NVMe SSD로 메모리 스와핑을 시작합니다. 이때 LLM의 토큰 생성 속도는 초당 25~40토큰에서 초당 0.5토큰 수준으로 급격히 추락(10~50배 감속)하여 에이전트 코딩이 사실상 불가능해집니다.

2. 에이전틱 코딩에서의 KV 캐시(Key-Value Cache) 중요성

트랜스포머 디코더 모델은 이전 토큰들의 Key 및 Value 벡터 표현을 메모리에 보관하여 매 토큰 생성 시 재계산하지 않도록 합니다.

코딩 에이전트는 파일 수정, 빌드, 테스트, 로그 분석 루프를 반복하면서 컨텍스트를 급격히 누적합니다. 32B 모델의 64k(65,536) 토큰 기준:

  • 표준 FP16 KV 캐시: 약 17.2 GB (가중치에 필적)
  • 8비트(q8_0 / FP8) KV 캐시: 약 8.6~9.1 GB (품질 영향이 대체로 미미한 권장 기본값, 모델/런타임별 상이)
  • Q4_0 KV 캐시: 약 4.8 GB (블록 스케일 메타데이터 포함 시 4.5 bpw)

3. 어텐션 구조별 메모리 영향 (MHA vs GQA vs MLA vs Hybrid)

  • MHA (다중 헤드 주의집중): Query, Key, Value 헤드 수가 동일하여 컨텍스트가 길어질 때 캐시 메모리가 가장 빠르게 폭증합니다.
  • GQA (그룹 쿼리 주의집중): 여러 쿼리 헤드가 하나의 Key/Value 헤드를 공유(예: 8:1)하여 캐시 메모리를 4~8배 절감합니다 (Llama 3.1, Qwen 2.5 등).
  • MLA (다중 헤드 잠재 주의집중): DeepSeek V2/V3 및 GLM-5에서 채택한 구조입니다. Key/Value 프로젝션을 512차원의 저차원 잠재 벡터(kv_lora_rank)로 압축하여 저장하므로, 표준 GQA 대비 약 5배 추가 캐시 압축을 달성합니다.
  • 하이브리드 선형 어텐션: GLM-5.3-Flash 및 Qwen3.6 MoE 등에서 사용하는 차세대 구조로, 전체 레이어 중 일부만 어텐션을 수행하고 대다수 레이어는 고정 크기 상태(State)를 유지하는 선형 어텐션을 결합하여 긴 컨텍스트에서도 캐시 증가를 극적으로 억제합니다.

4. 신뢰성 계층(Epistemic Decomposition) 및 정밀 블록 모델링

메모리 추정치는 네 가지 명확한 근거 수준으로 분리되어 투명하게 제공됩니다:

  • 모델 가중치 (Mweights): Hugging Face API를 통해 다운로드 가능한 실제 분할 샤드 파일 바이트의 정확한 합산 (또는 베이스 모델의 파라미터 기반 휴리스틱).
  • KV 캐시 (MKV): 풀 어텐션 레이어 수(Nfull), 선형 어텐션 고정 순환 상태(Nlinear × Sstate), 그리고 GGML 블록 양자화 메타데이터 오버헤드(q8_0: 8.5 bpw / 1.0625 B, q4_0: 4.5 bpw / 0.5625 B, q5_0: 5.5 bpw / 0.6875 B)를 정밀 반영한 아키텍처 기반 계산. K와 V 캐시의 비대칭 포맷 지정 지원.
  • 활성화 스크래치패드 (Mscratch): 어텐션 작업 영역, 연산 그래프, MoE 라우팅 버퍼 및 프리필 청크(ubatch)를 모델링한 백엔드 휴리스틱.
  • 시스템 헤드룸 (Mheadroom): macOS 커널, WindowServer, 외장 모니터 프레임버퍼, IDE 등을 위한 사용자 정책 기반 예약 공간(기본 6.0 GB).

5. macOS Metal 작업 세트 한계와 물리 RAM 제약

Apple Silicon 환경에서는 두 가지 서로 다른 제약 조건을 동시에 검토해야 합니다:

  • 물리 RAM 제약: 전체 메모리가 시스템 물리 RAM 이하(Mtotal ≤ MRAM)여야 NVMe SSD 스와핑 병목을 방지할 수 있습니다.
  • Metal 프로세스 할당 한계 (~75%): macOS는 단일 프로세스가 할당할 수 있는 GPU/Metal 메모리를 기본적으로 물리 RAM의 약 75%(Mruntime ≤ 0.75 × MRAM)로 제한합니다. 런타임 메모리가 물리 RAM에는 들어가지만 75%를 초과할 경우, sudo sysctl iogpu.wired_mem_limit 튜닝이 필요합니다.
